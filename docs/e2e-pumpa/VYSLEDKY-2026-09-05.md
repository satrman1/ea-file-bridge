## Nálezy

### N1 — P7: proklik na package/diagram z Output tabu živě nefunguje (1a nedoloženo)

Co se stalo: dvojklik na řádek `[vytvoreno] package "P4 Mail (pumpa)" … (pkg:1076)` a na oba diagramové řádky `(dgm:1159)` nic neoznačil; debug řádek `dblclick debug v5: tab='AI Bridge' id=0 how=[val,val,val] … line='  [vytvoreno]  package "P4 Mai'`. Žádný řádek `Navigace na pkg … selhala` (výjimka tedy nepadla, nebo se k volání nedošlo).

Proč ✅ u UC/scenarios/constraints **nic nedokazuje o markeru**: ty řádky nesou ElementID i ve 3. parametru `WriteOutput` a EA na něj naviguje **nativně** (Log.js, iterace 5). Handler s markerem se u nich vůbec neprojeví. Package a diagram řádky mají 3. parametr 0 (jiný číselný prostor) a stojí **jen** na markeru + `ShowInProjectView` z handleru — a právě ty selhaly.

Klasifikace: **chyba kódu nebo prostředí — nerozhodnuto.** Debug v5 tiskne prvních 30 znaků, marker je na konci řádku; z živého záznamu nelze říct, zda `LineText` do handleru dorazil celý. Tři hypotézy v pořadí pravděpodobnosti:
1. `Repository.ShowInProjectView(Package|Diagram)` z add-in kontextu **neoznačí** (analogie nálezu 21. 8. c, kdy `GetElementByID(Package.Element.ElementID)` + `ShowInProjectView` package neoznačil; pro Diagram objekt to nikdo živě neověřil). Pak je marker v pořádku a je potřeba jiná navigace (např. `Repository.ShowInProjectView` na `Package.Element`, nebo Add-in Search `FB_Changes` s CLASSGUID/CLASSTYPE Package/Diagram = nativní cesta, která u elementů prokazatelně funguje).
2. EA předává `LineText` zkrácený/pozměněný (např. bez koncové části) → regex `\((el|pkg|dgm):(\d+)\)\s*$` nesedne, `target` zůstane 0 a handler tiše skončí.
3. `GetPackageByID/GetDiagramByID` vrátí null (nepravděpodobné — ID jsou z téže session).

Oprava v tomto vlákně (diagnostická, `EA_OnOutputItemDoubleClicked` **v6**, +8 řádků): debug tiskne `len=`, `head=` (30) a **`tail=` (40 znaků)** řádku; nový řádek `dblclick nav: marker=… kind=… target=…` a po dispatchi `-> ShowInProjectView zavolano | objekt NENALEZEN`. Příští běh rozhodne mezi hypotézami jedním dvojklikem. Design (co dělat, když platí 1) → zápřah **Z260904-1c**, ne oprava naslepo.

### N2 — P8: smazaný package v `items` bez PackageID/jména/cesty (chyba kódu, opraveno)

`FB_OpDelete` větev PACKAGE pushovala `{type, id: t.id || 0, deleted}` — u cíle zadaného GUIDem `id:0`, bez `name`/`path`; `FB_LogChanges` proto vypsal `[smazano] Package "" (id 0)`. Větev ELEMENT to dělala správně (jméno + cesta **před** smazáním, §9c). Oprava: PackageID + Name + `FB_ElementPath(package)` zachytit před `DeleteAt`; větev DIAGRAM dostala aspoň `name`. Harness test `FB_OpDelete: Package podle GUID -> items nese PackageID, name, path (P8 nalez)` → 221/221. **Nasazení**: `deploy_src` `FB_OpDelete` pumpou (bez restartu EA — běží v pumpě).

### N3 — P5/P5b: placeholdery nenahrazeny (chyba obsluhy; kód OK)

`req-P5.json` i `req-P5b.json` šly do pumpy s texty `GUID-PKG-Z-P4` / `GUID-UC-Z-RES-P5`. Kód reagoval správně a bezpečně: Risk Gate označil neresolvovatelný cíl fail-closed ELEVATED (popup s důvodem „Neresolvovatelny package 'GUID-PKG-Z-P4' … fail-closed"), po Ano executor vrátil `E_NOT_FOUND`, zbytek `skipped`, soubor do `processed\`. Nic se do modelu nezapsalo (UC „Prijmi zpravu (pumpa)" nevznikl).

Důsledek: řetěz „op 1 ok → op 2 chyba → oprava z res" je pumpou **nedoložen** (schránkou doložen T7-03/03b 31. 8.). Poznámka k protokolu: popup ELEVATED **ukázal** důvod „neresolvovatelný cíl" a přesto se odklikl Ano — návod P5 má napřed říct „pokud v popupu čteš *Neresolvovatelny* + název placeholderu, dej Ne a oprav soubor". Zvážit (zápřah, ne teď): FB_Main odmítnout request, v němž zůstal literál `GUID-` (E_ARGS „nenahrazený placeholder"), ať se to nedostane ani k popupu.

### N4 — P2: kde je ACK u transportu pumpa (nález, rozhodnutí: **NE**, chat verzi na konzoli nevypisovat)

Doloženo: pumpa `FB_ChatRender` nevolá; identita výsledku (GUIDy, cesty, warnings) je **výhradně** v `res-<id>.json`; Output tab dává jednořádkový souhrn `FB <id> -> <status>: N ops (…)` + u zápisů výpis změn; schránka zůstává nedotčená (test `KONTROLA` ✓). Totéž platí pro GUI fallback (P9).

Doporučení **NE**, důvody: (1) konzumentem pumpy je nástroj/agent se souborovým přístupem (Copilot ve VS Code, Claude) — čte `res-*.json`, což je system of record; chat ACK vznikl pro kanál, kde AI soubor číst nemůže (schránka/chat). (2) Konzole pumpy není strojově ani spolehlivě lidsky přenosná (cscript konzole, kódování, žádný Ctrl+V do chatu bez ručního výběru) — text by byl třetí, neautoritativní kopií téhož. (3) Duplicitní vykreslování porušuje kontrakt §3a „jeden ACK per kanál" a přidává údržbu (každá změna FB_ChatRender = dvě místa k ověření). (4) Neutralita pumpy vůči iteraci 7 je právě to, co P2 dokázal — měnit ji bez potřeby by test znehodnotilo. Pokud se ukáže potřeba lidsky čitelného souhrnu na konzoli, stačí **jeden řádek** (`status`, počty ok/chyb, jméno res souboru) — ne chat verze. Kandidát do backlogu, ne do 1c.
