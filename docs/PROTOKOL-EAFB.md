## 1. Architektura

```
AI driver (Copilot/Claude)          pumpa (pump.wsf, WSH)            EA (běžící instance)
  píše requests\req-*.json  ──►  watcher ~1 s, COM attach   ──►  executor = kód operací FB_*
  čte responses\res-*.json  ◄──  zapíše response, archivuje  ◄──  z elementu AICodeBridge (11037)
```

- **Kanon kódu = `src/` v repu**; runtime kopie žije v modelu (element AICodeBridge). Nasazení změn = dávka `deploy_src` (pumpa si kód po dávce sama přenačte). Bootstrap v EA Scripting je jen nouzový fallback.
- **Zápis výhradně Automation API.** `Repository.SQLQuery` jen čtení (vrací i GUIDy).
- Složky vedle `pump.wsf`: `requests\` (vstup), `responses\` (výstup), `requests\pending\` (**v0.8**: ELEVATED dávky čekající na lidské potvrzení), `requests\processed\` (archiv s timestampem), `requests\rejected\` (nevalidní/odmítnuté/zamítnuté).
- Životní cyklus souboru: `req-X.json` → zpracování → `res-X.json` + přesun requestu do `processed\` (`rejected\` u E_PARSE, E_RISK_BLOCKED, E_RISK_CONFIRM), **nebo** (v0.8, ELEVATED) → `pending\` beze změny jména + `res-X.json` se stavem `confirm_required` → po potvrzení/zamítnutí člověkem `processed\`/`rejected\` a přepis `res-X.json` finálním výsledkem. Podsložku `pending\` pumpa i GUI fallback strukturálně přeskakují (výpis bere jen soubory přímo v `requests\`) — čekající dávka nikdy nerotuje ve smyčce. Při zavřeném EA request čeká ve frontě a zpracuje se po re-attachi; čekající dávka v `pending\` restart EA i pumpy přežije (bezstavovost, §6e).
- **Kontrakt executoru (I5, v0.8):** `FB_Main(Repository, requestText)` přijímá přednostně **cestu k req souboru** (pumpa v0.5 i `FB_ProcessFolder` předávají cestu) — SHA-256 surových bajtů i JSON parse proběhnou nad týmž jedním čtením souboru (`FB_FileBytes` + `FB_Utf8Decode`), žádné mikro-TOCTOU okno. Text začínající `{` = zpětně kompatibilní fallback (ELEVATED v textovém režimu nelze potvrdit — fail-closed `confirm_required` bez nonce, nic se neprovede).

### 1a. Dvojí runtime a `FB_ComObj` (lekce 2026-08-17)

Stejný kód operací běží ve **dvou různých JS runtime**:

| Runtime | Engine | COM objekty | Enumerator |
|---|---|---|---|
| pumpa (pump.wsf, WSH) | JScript | `new ActiveXObject(...)` | ano |
| EA in-model add-in (GUI fallback, prod strana M365-A) | JavaScript (Mozilla) | `new COMObject(...)` | **ne** |

Pravidla:

1. Kód, který může běžet v obou runtime (GUI fallback, linked docs), tvoří COM objekty **výhradně přes `this.FB_ComObj(progId)`** (zkusí ActiveXObject, fallback COMObject). Přímý `new ActiveXObject` v EA runtime hodí ReferenceError a **tiše shodí celý handler** — u uživatele „klik nic neudělal".
2. `Enumerator` v EA runtime neexistuje — výpis složky řeší `FB_ProcessFolder` fallbackem přes skrytý `dir /b` (WScript.Shell.Run, okno 0, wait).
3. **Aktivace nového kódu v EA runtime = plný restart EA.** `File → Reload Current Project` na EA 17.1.5 (build 1715) NEobnovil ani strukturu menu, ani těla operací add-inu (ověřeno 2026-08-16/17; dřívější lekce „reload stačí" z 2026-07-19 pro tento účel neplatí). Pumpa restart EA přežije (re-attach); `deploy_src` se týká jen runtime pumpy.
4a. **EA runtime NEDRŽÍ in-memory stav `this._fb*` mezi invokacemi** (lekce 2026-08-20, živý E2E iterace 5: spike klikal 2× „krok 1"): každé vyvolání add-inu (menu, search, broadcast) dostává čerstvou instanci — na rozdíl od pumpy, kde JScript proces žije. Stav, který má přežít mezi kliky (čítač spiku, poslední zapisová dávka pro `FB_Changes`, W8 flag „první zápis po E_EXCEPTION"), bydlí ve **state souborech `<baseDir>\state-<name>.txt`** (`FB_StateFile` — read/write/delete, best-effort). In-memory vzory (`_fbConfirmCtx`, `_fbSessionStarted`…) fungují spolehlivě jen v pumpě; `_fbConfirmCtx` je záměrně in-call (nesmí přežít), `_fbSessionStarted` v EA runtime jen způsobí opakovaný (idempotentní) session start. Broadcast handlery v model add-inu navíc **nedostávají COM signaturu** — přijde `(Repository, Info)`, kde `Info` = EventProperties (`Info.Get(i).Name/.Value`; vendor vzor EA_OnPreDeleteAttribute) — handler musí číst properties jménem i pozicí.

4. **COM chyby v EA runtime NEJSOU zachytitelné try/catch** (lekce 2026-08-19, T5-10): např. přiřazení binárního VARIANTu z `ADODB.Stream.Read` do MSXML `node.nodeTypedValue` hází „Nesoulad typů", výjimka projde skrz JS try/catch a shodí CELOU invokaci add-inu („Invocation error in: addin.EA_MenuClick" v System Output, u uživatele „klik nic neudělal" — žádný dialog, žádná response). Binární čtení souborů (`FB_FileBytes`) se proto pouští jen v JScript runtime; EA runtime čte soubory textově utf-8 (hash textu ≡ hash surových bajtů pro UTF-8 soubory bez BOM). Stejná past pravděpodobně platí pro `get_diagram_image` s `inline: true` v EA runtime (base64 přes MSXML) — neověřeno, inline používat jen přes pumpu.

## 2. Request (1 soubor = 1 dávka)

```json
{
  "protocol": "eafb/0.2",
  "id": "20260817-01",
  "repo": "EAExample.qea",
  "ops": [
    { "op": "ping", "echo": "text" },
    { "op": "create_or_update_package", "parent": "{GUID}", "name": "Pkg" },
    { "op": "create_or_update_elements", "elements": [ { "package": "$1", "name": "X", "type": "Class" } ] }
  ]
}
```

- `repo` — deklarace cílového repozitáře (case-insensitive podřetězec identity dle `FB_RepoId`: u MS SQL název DB přes `DB_NAME()`, u lokálního `.qea` fallback ConnectionString). Volitelné v protokolu, **povinné v copilot-instructions**. Při neshodě se neprovede NIC (ani audit) → `E_REPO`.
- Sémantika dávky: **stop-on-error** — první chyba zastaví zbytek (`skipped`).
- `notes` plain text (JSON escapování zvládá diakritiku i tab); `notes_b64`/`sql_b64` = záloha.

### 2a. `$N` řetězení GUIDů v dávce

Kterákoli string hodnota v opu může odkázat na výsledek dřívějšího opu téže dávky:

| Zápis | Význam |
|---|---|
| `"$0"` | `results[0].guid` |
| `"$0.id"` | `results[0].id` |
| `"$1[2]"` | `results[1].items[2].guid` |
| `"$1[2].id"` | `results[1].items[2].id` |
| `"$1[2].compositeDiagram"` | **v0.22 (N‑RE‑11):** `results[1].items[2].compositeDiagramID` — kompozitní diagram prvku založeného touto dávkou (Automation `CompositeDiagram`, jinak `t_diagram.ParentID`; vč. auto‑kompozitu MDG — UCR, LS, UC detail, SR/DTO s `isComposite`). Bez indexu = první položka. Risk Gate ho bere jako **vlastní** diagram (B3 OWN), prvek bez kompozitu = `E_ARGS` s nápovědou |

Reference se rozresolvují rekurzivně v celém objektu opu (i uvnitř polí `targets`, `elements`, `taggedValues.ids`…). Nerozresolvovatelná reference = chyba opu. Do SQL řetězců `$N` NElze vkládat (nahrazuje se jen celá hodnota pole).

## 3. Response

```json
{
  "protocol": "eafb/0.2", "id": "...", "status": "done | error | confirm_required | rejected",
  "repository": "identita dle FB_RepoId", "connection": "cesta připojení (informativní)",
  "results": [ { "op": "...", "status": "ok | error | skipped | pending", "...": "..." } ],
  "warnings": [ "jen když je co hlásit (např. ignorované confirm: true, W6)" ],
  "risk": { "riskLevel": "...", "riskReasons": [], "metrics": {}, "summary": {}, "payloadHash": "...", "confirm": { "required": true, "confirmedByUser": true, "channel": "pumpa|gui|okno", "timestamp": "..." } },
  "confirm": { "nonce": "jen u confirm_required", "payloadHash": "plný hash", "hashPrefix": "12 znaků", "pendingPath": "..." },
  "audit": { "aiLogGuid": "{...}" }
}
```

Zápisové výsledky nesou `guid` + `id` (a `items[]` s `{guid, id, name, created}` u dávkových operací) — kvůli `$N` referencím. **`confirm_required` (v0.8)**: žádný zápis neproběhl, dávka čeká v `pending\`; top-level blok `confirm` s nonce žije **výhradně v `res-*.json`** — do chat verze smí jen `hashPrefix` (§6e pravidla). `rejected` = dávka zamítnuta člověkem (`E_RISK_REJECTED`) **nebo vypršela (`E_RISK_EXPIRED`, v0.16)**.

### 3b. Stavy `res` — odpověď jako stavový záznam dávky (v0.16, balík B1 — Z261004b-3, revize usability pumpy P1)

> **Ověřeno živě doma 11. 10. 2026 22:36–22:59** (`docs/e2e-pumpa/VYSLEDKY-2026-10-11-B1.md` kap. 5): 13/13 scénářů §3b–3d — `processing`/`since`, `E_INTERRUPTED` po zavření pumpy uprostřed dávky, `E_DUPLICATE_ID`, `E_UNKNOWN_OP`/`E_ARGS` bez okna, znovu poslaná čekající dávka = okno znovu bez restartu, pravidlo 3 bez oken, `riskPolicy` v pingu, kontrola parametrů 0 rozdílů.

V kanálu se souborem (pumpa, GUI fallback, schránka) je `responses\res-<jméno>.json` **stavový záznam dávky**, ne jen její výsledek. `FB_Main` ho zapíše **sám při převzetí** (`{"protocol":"eafb/0.2","id":…,"status":"processing","since":"RRRR-MM-DD HH:MM:SS","repository":…,"file":…}`) a adaptér ho po doběhnutí přepíše konečným výsledkem jako dosud. Každý `res` od v0.16 nese `since` = čas převzetí dávky (u `confirm_required` tedy „čeká od"; po re-klasifikaci zůstává původní).

| `res-<jméno>.json` | Význam pro agenta | Co dělat |
|---|---|---|
| neexistuje | pumpa dávku **nepřevzala** (neběží, čeká na EA, stojí na okně jiné dávky) | zeptat se člověka na okno pumpy; **neposílat znovu** |
| `status: "processing"` | pumpa na dávce **pracuje** (dlouhý dotaz, dialog EA) | čekat; `since` říká od kdy |
| `status: "confirm_required"` | čeká na **člověka** v okně (`pending\`) | čekat bez limitu; když člověk řekne, že okno zmizelo, poslat **tentýž soubor** znovu (§3c) |
| `done` / `error` / `rejected` | **výsledek** (konečný stav) | číst; pro navázání použít GUIDy z výsledku, ne opakování dávky |

Z toho plynou kontroly při převzetí **zápisové** dávky (čtecí dávky se smějí opakovat beze změny):

- vlastní `res` ve stavu `processing` se stejným `id` = dávka byla **přerušena** (zavřená pumpa / pád EA uprostřed) → **`E_INTERRUPTED`**, nic se neprovede (model může nést část zápisů — agent zkontroluje Output tab a pošle *opravnou* dávku s novým id);
- konečný `res` se stejným `id` → starý `res` do `responses\superseded\res-<jméno>.<čas>.json` a **`E_DUPLICATE_ID`** (dřív by se dávka provedla znovu a vznikly duplicity — simulace V3); stejné jméno souboru s *jiným* id = jen přesun starého `res` do `superseded\`, dávka proběhne.

### 3c. Čekající dávka (v0.16, P3 — KONCEPCE potvrzovací okna pravidlo 6)

- **Znovu poslaný tentýž soubor** (stejné jméno, stejný obsah) **neničí potvrzení**: `FB_Main` vrátí stávající `res` čekající dávky **beze změny** (stejný nonce), nový exemplář odloží do `requests\rejected\<jméno>.<čas>.duplicate.json` a pumpa okno nabídne znovu — bez restartu (FB-PU-15/-16, simulace S1).
- **Stejné jméno, jiný obsah**: `res` čekající dávky zůstává nosičem nonce (chyba místo něj by potvrzení zničila — přesně FB-PU-16), přibude `warnings[]` „DUPLICITA ID: pod tímto id už čeká jiná dávka…" a sekce `duplicate {kind: "same-id-other-content", pendingId, newExemplar}`; nový exemplář jde do `rejected\`, agent pošle dávku s novým id. *Vědomá odchylka od KONCEPCE („chyba"): kód chyby by přepsal `res` = jediný doklad pro potvrzení.*
- **Stejný obsah pod jiným id**: `E_DUPLICATE_ID` s `duplicate {kind: "same-content-pending", pendingId, pendingFile, since}` — druhá kopie se nezařadí (FB-PU-17). Zdroj: index čekajících dávek `requests\pending\.index.txt` (`FB_PendingIndex`; řádek `jméno|otisk|id|since`, ověřuje se proti disku, pumpa i GUI fallback berou z `pending\` jen `*.json`).
- **Expirace**: dávka starší než `confirmMaxAgeMin` (klíč `FB_RiskPolicy`, chybí = 480 min) se neprovede — při pokusu o potvrzení i zamítnutí vrátí `FB_ConfirmPending` **`E_RISK_EXPIRED`** (`status: "rejected"`), soubor jde do `rejected\`, audit se zapíše (`confirmedByUser: false`, `channel: "expired"`). Pro nabídku po startu pumpy slouží `FB_PendingSweep(Repository, pendDir)` — expirované přesune, přepíše jejich `res` a vrátí seznam k vypsání (pumpa v0.6 — Z261004b-5; pumpa v0.5 je nabídne oknem a expirace zabere až po kliknutí).

### 3d. Předběžná kontrola dávky (v0.16, P2 — KONCEPCE pravidlo 1 „chyba agenta okno neotvírá")

`FB_Precheck` běží ve `FB_Main` hned po parsování a kontrole repozitáře (`E_REPO`), ve dvou fázích: **před kontrolou přístupu** (operace v registru → jinak `E_UNKNOWN_OP` s `suggestions[]`; povinná pole a tvary; žádný prázdný seznam; žádný zástupný text `<…>`, `GUID-…`, `{GUID-` v identifikačních polích — `guid`, `package`, `parent`, `owningElement`, `element`, `diagram`, `source`, `target`, `repo`, položky `elements[]`/`diagrams[]`/`packages[]`…; textová pole jako `notes` se nekontrolují; `$N` jen na dřívější operaci) a **po ní** (`E_ADDIN_ACCESS` má přednost: operace povolená ve `FB_OpsAllowed` → jinak `E_OP_FORBIDDEN`; cíl zadaný GUIDem u zápisové operace v modelu existuje — dohledání přes `FB_TargetCache`, tatáž mezipaměť pak slouží Risk Gate). Výsledek = **jedna chyba se všemi problémy** v `problems[] {op, path, code, message, suggestions?}`, všechny `results[]` `skipped`, **žádné okno, žádná záloha, žádný audit** (hák pro auditované kódy — `E_BLACKLIST`, Z261004b-10 — je připravený). Chyby odkazů `$N` při exekuci vrací `E_ARGS` s nápovědou („použij `$0[0]`"), ne `E_EXCEPTION`; příznak W8 (první zápis po pádu jde oknem) se nastavuje jen po skutečné výjimce z EA/COM. Fail-closed Risk Gate zůstává pro to, co předem zjistit nejde (cíl jménem, `$N` na výsledek čtení, objem klonu, rozpočet).

### Kontrakt chat verze (iterace 7, zadání v1.1 2026-08-30)

Dřívější stav („datový výcuk jen u `query`, zbytek stavový řádek") byl kořenem nálezu z živého E2E 2026-08-21: agent ve schránkovém kanálu neměl z ACK jak pokračovat a prosil o `res-*.json`. Od iterace 7 platí:

**Čtyři třídy tvarů** (normativní rozpad = Příloha A red team reportu `RedTeam-Zadani-Iterace-7-Schrankovy-Kanal-2026-08.md`; projekční tabulka `PROJ` žije **v kódu** `FB_ChatRender`, úplnost proti registru `REG` hlídá harness — kritérium 11′):

| Třída | Počet | Projekce do ACK |
|---|---|---|
| **A** — `count` + `items[]` | 27 | generická větev: identita položek (`guid`, `name`, `type`/`stereotype`, u packages `path` plnou cestou) |
| **B** — `rows[]` + `rowCount` | 1 | `query` — kompaktní výcuk řádků (beze změny) |
| **C** — singletony | 8 | vlastní projekce (`ping`, `get_selected_context`, `baseline_diff`, `create_baseline`, `create_element`, `clone_package`, `find_or_create_referencing_sr`, `deploy_src`) |
| **D** — číselné shrnutí bez `items[]` | 6 | diagramová rodina: `op` + `status` + počet + ukazatel na res — nikdy prázdný segment |

**Projekce = jen identita, nikdy obsah:** do chat verze jde z položky výhradně `guid`, `name`, `type`/`stereotype`, u packages `path` (plnou cestou — jednotně pro whitelist v pingu, projekci packages i `get_selected_context`). **Nikdy** `notes`, `XMLContent`, `raw`, `rtf_b64`, `png_b64`, těla scénářů, atributy ani operace; vnořené `messages[]` jen počtem. Binární/souborové výstupy (`get_diagram_image`, `export_element_linked_documents`) nesou v ACK cestu + explicitní větu, že obsah schránkou neprojde. Neuvedená operace má **bezpečný default**: `op` + `status` + číselné shrnutí + ukazatel na res — nikdy prázdný render u `status: "ok"`.

**Výjimka B3 — `create_or_update_constraints` a `create_or_update_requirements`:** položky GUID nemají a mít nemohou (v datovém modelu EA neexistuje — `t_objectconstraint`, `t_objectrequires`). Identita v ACK = **element GUID (`res.guid`) + `name`+`type` položky**; oprava po chybě = **rebuild kompletní sady na element** (§5a bod 8), ne adresace položky.

**Rozpočty a priorita ořezu:** defaulty žijí v kódu (`total: 4000`, `perOp: 900`, `items: 25`, query 700, warn 500); `FB_Config` sekce `chat` je jen volitelný per-repo přepis (chráněný element, PROTOKOL §8 bod 7). W10 platí beze změny (nikdy tichý cut, vždy ukazatel na `res-<id>.json`) a přibývá **pořadí ústupu**: 1. počet warningů + chybový kód (první řádek), 2. **GUIDy**, 3. jména, 4. typy/cesty/doprovod. Dojde-li rozpočet, zahazují se nejdřív jména a GUIDy zůstávají — agent s GUIDem bez jména pracovat umí, obráceně ne. **Ořez se provádí po hranicích položek — ACK nikdy nenese neúplný GUID (W2);** výsledný řetězec se nestříhá substringem.

**`ping` = úvodní kotva session:** vrací navíc **`writeScope{}`** (od v0.17, §6k — místo `whitelist[]`: `mode: "blacklist"`, `securityEnabled`, `cascadeDelete`, `summary` = tatáž lidská věta jako start session a *Stav bridge*, `blacklist[{guid, name, path, note, found, allowIncomingRefs}]`, `implicit[]`, `problems[]`, `warnings[]`, `agentNotes[]`; chat ACK renderuje segment `zapis: blacklist (N chranenych vetvi, EA security zapnuta/VYPNUTA): <cesty>` a případné `KONFIGURACE CILE ZAPISU VADNA (E_SCOPE_CONFIG)`), a `access{level, securityEnabled, reason}` z `FB_UserAccess`. `login`/`groups` se v chat verzi nerenderují (datová minimalizace, ne bezpečnostní plot — dispozice 2026-08-30), `connection` se do ACK nedává. **`E_REPO`** v chat verzi **pojmenuje připojený repozitář** (basename souborové cesty) — agent se opraví sám bez ztraceného kola.

I3 platí beze změny: chat ACK není nikdy jediný záznam, `res-*.json` zůstává system of record — mění se jen to, kolik z něj agent potřebuje.

**Tvar `res-*.json` (v0.13, nález N4):** response z `FB_Main` je **odsazená** (jedna mezera na úroveň, odřádkování, **bez mezery za dvojtečkou** — kotvy `"code":"E_PARSE"`, `"status":"confirm_required"`, `"reloadCode":true`, které pumpa a `FB_ConfirmPending`/`FB_ProcessFolder`/`FB_ClipboardImport` hledají v textu, zůstávají doslovně); obsahově beze změny, konzumenti parsují (`FB_JsonParse`, `ConvertFrom-Json`). Chat ACK (`FB_ChatRender`) se nemění; `payloadHash` se počítá ze surových bajtů **req** souboru, z res textu nikdy.

### Warnings — sémantika a propsání do chat ACK (v0.11, nález POC N-7)

**Co warning znamená:** operace skončila `status: "ok"`, **zápis proběhl**, ale **část deklarovaného záměru se nepropsala** — a executor přesně ví která. Warning tedy **není** chyba (nemá `code`, nezastaví dávku, nespustí stop-on-error) a **není** ani QC nález (QC je kontrola *po* zápisu, §3.4/W6). Je to *tichá díra mezi zadáním a výsledkem*, kterou nic jiného neohlásí: počty souhlasí, `status` je `ok`, ACK vypadal dřív úplně čistě.

**Dvě úrovně, obě v response:**

| pole | kdo plní | příklad |
|---|---|---|
| `results[i].warnings[]` — **op-level** | 14 zápisových operací (`elements`, `package`, `connectors`, `messages`, `attributes`, `operations`, `scenarios`, `constraints`, **`requirements`**, `diagram`, **`move_elements`**, `apply_classifier_stereotypes`, `find_or_create_referencing_sr`, `deploy_src`) | `scenarios[1]: join 'BE95002' neni cislo kroku …` (§6b); `elements[0]: pole 'package' u existujiciho elementu NEPRESOUVA … pouzij move_elements` (§6i); chybějící šablona ve scaffoldu (§6b) |
| `warnings[]` — **dávkové** | `FB_Main` | migrace W6: `confirm: true` v dávce ignorováno (§6e) |

**Chat ACK (od v0.11):** `FB_ChatRender` obě úrovně sloučí a vykáže je takto:

```
EAFB OK 20260821-83: 6/6 ops | 1 WARNING: scenarios[1]: join '2' neni v davce - Join nezapsan | QC ciste (3 kontrol)
Warnings (zapis PROBEHL, cast zameru se ale nepropsala - resit OPRAVNOU davkou, ne preposlanim):
- op[4] create_or_update_scenarios: scenarios[1]: join '2' neni v davce - Join nezapsan
```

Pravidla tvaru (kontrakt, hlídá harness):

1. **Počet + první warning jsou v PRVNÍM řádku** (`| N WARNING:` / `| N WARNINGS:`) — právě proto, aby přežily deterministický ořez rozpočtem (W10; priorita ořezu viz kontrakt výše, rozpočet `total` default 4000). Segment stojí **před** QC segmentem.
2. **Bezwarningová dávka má ACK beze změny** — žádný prázdný segment, žádný „0 warnings". Regrese je v harness testu.
3. Výpis pod prvním řádkem má vlastní rozpočet (500 znaků) a při přetečení končí ukazatelem `(dalsich N - plny vycet v res-<id>.json)` — **nikdy tichý ořez** (W10).
4. Warningy se vykazují i v **chybové** větvi ACK (`EAFB CHYBA …`) — warning z operace, která doběhla před chybou, nesmí zmizet.
5. Warning se řeší **opravnou dávkou dle textu warningu** (§5a), nikdy přeposláním téže dávky.

**Pro klienta (Copilot/skill):** ACK od iterace 7 nese identitu výsledků (GUID + jméno) a warningy — **prosba o `res-<id>.json` je výjimka pro doložené případy** (dumpy nad rozpočet, binární výstupy, plný výčet warningů nad rozpočet), ne výchozí postup.

1. **Rollback neexistuje.** Dávka je stop-on-error; chybová response nese v `items` GUIDy položek **dosud vytvořených** uvnitř chybující operace — ty v modelu zůstávají. Operace za chybou jsou `skipped` (neproběhly vůbec).
2. **Korektní retry bez opt-in polí = opravná dávka adresující GUIDy z chybové response** (guid → UPDATE cesta), **nikdy slepé přeposlání celé dávky** — každé přeposlání create položek bez guid vytvoří duplicity. Toto pravidlo platí bezpodmínečně, dokud klient nepoužívá `matchByName`/`match`/`dedupKey`.
3. **Opt-in idempotence (v0.5)** — s těmito poli je přeposlání téže dávky bezpečné (druhý běh = UPDATE, `created: false` + `matchedBy` v items):
   - `matchByName: true` (elements, packages — K1): find dle jména/aliasu **scoped na cílový package (`Package_ID` + `ParentID = 0`) / parent element (`ParentID`) / parent package (`t_package.Parent_ID`)**. Globální resolver `FB_ResolveEl` se pro tohle nepoužívá.
   - `match: "composite"` (connectors — K2): lookup dle (`Start_Object_ID`, `End_Object_ID`, `Connector_Type`, `Stereotype`); právě 1 nález = UPDATE.
   - `dedupKey` (elements, connectors — K4): stabilní klientský klíč; na create se zapíše jako TV `ai.dedup` (sdílený helper `FB_DedupFind`, SQL `t_objectproperties`/`t_connectortag`, bez dialektových funkcí). **Přežívá přejmenování.** Pořadí lookupu: guid → dedupKey → kompozit/jméno.
   - `rebuild: true` (messages — K3): server-side V2d — smaže **všechny** Sequence konektory diagramu (kontrola cíle zápisu drží — od v0.17 blokuje jen zprávu s oběma konci v chráněné části, §6k; pre-check před prvním mazáním = žádné parciální mazání) a postaví znovu z dávky; vyžaduje `diagram` + explicitní `seqNo` u každé zprávy; response nese `removed`. Vzor `create_or_update_scenarios`.
4. **`E_AMBIGUOUS`**: match/dedupKey lookup našel >1 kandidáta — response nese `guids` (výčet). Řešení: adresovat konkrétní `guid`, nebo u konektorů poslat `dedupKey` (create pak založí nový, jednoznačně klíčovaný).
5. **Vazba na modal hang** (T4-3): po zotavení z visící pumpy odklikem hrozí falešné OK `rowCount: 0` — právě tam vzniknou duplicity nepozorovaně. Retry po každém zotavení proto **výhradně** s `match`/`dedupKey`, nebo přes kontrolní čtení + opravnou dávku dle bodu 2.
6. Výchozí chování beze změny: create bez opt-in polí je vždy `AddNew` — dávky, které duplicitní jména legitimně chtějí (nepojmenované lifeliny, opakovaná jména v různých kontextech), fungují jako dřív.
7. ⚠ **`matchByName` × `$N` se sčítají do riskových prahů** (lekce 2026-08-21, dávka 20260821-61, kulisa SportHub): opt-in idempotence je pro Risk Gate **nejistota** — `matchByName`/`dedupKey` konzervativně přičítá `updatedExisting` (§6d) a `$N` reference v takové dávce nejde přiřadit ke create větvi (fail-closed B3), takže cíle počítají jako **existující** prvky a jejich packages jako **cizí**. Scaffold „package + podpackages + obsah" s `matchByName: true` proto spadl na `E_RISK_BLOCKED` (`affectedPackages 6 > 5`), přestože nic v modelu neexistovalo. Praktické pravidlo pro klienty (Copilot, skilly, vrátný): **strukturu zakládej po dávkách s jednou cílovou package** (`affectedPackages > 1` je práh ELEVATED) a GUIDy z předchozí response adresuj přímo; `matchByName` zapínej tam, kde je retry pravděpodobný, ne plošně — když recon prokázal, že cíl neexistuje, je create bez opt-in polí levnější i pro gate. Není to chyba gate (fail-closed je záměr), ale past sestavování dávek. **Protidůkaz k dřívějšímu doporučení „dělit dávky podle velikosti" (nález N-5, POC R1):** táž práce poslaná jako **jedna** dávka o 6 operacích (`writeOps 19`, `createOps 9`, `affectedPackages 2`) **bez** `matchByName` skončila jako ELEVATED a po potvrzení proběhla bez problému. Spouštěčem BLOCKED tedy nebyla velikost, ale kombinace opt-in idempotence a `$N`. Pravidlo zní: **strukturu zakládej po dávkách s jednou cílovou package** (`affectedPackages > 1` je práh ELEVATED, ne BLOCKED) a **`matchByName`/`dedupKey` zapínej jen tam, kde je retry pravděpodobný** — ne plošně a ne jako „pro jistotu". Salámování dávek podle velikosti se tím **ruší** jako doporučení.
8. **GUIDy pro retry jsou od iterace 7 přímo v chat ACK** (§3a kontrakt) — opravná dávka se ve schránkovém kanálu skládá z GUIDů renderovaných v ACK, bez sahání na `res-*.json`; chybová větev ACK nese i GUIDy položek vzniklých před chybou. **Výjimka B3** (`create_or_update_constraints`, `create_or_update_requirements`): položky GUID nemají — ACK nese element GUID a retry = **rebuild kompletní sady na element GUID** (obě operace jsou deterministický rebuild, dávka vždy nese kompletní sadu).

## 6d. Risk Gate — výpočetní část (iterace 4b, v0.7, dávky 20260819-05…19)

Risk-based HITL dle zadání 4b v1.1 (red team GO s podmínkami, dispozice B1–B4/W1–W9 závazné). **Tato fáze = jen výpočet a shadow**: metriky + klasifikace se počítají a vykazují, vynucuje se výhradně BLOCKED. Confirm okruh (ELEVATED → `confirm_required`, nonce, `requests\pending\`, `E_RISK_INTEGRITY`, bezstavová re-klasifikace, migrace `confirm: true` u klonů) postaven jako **V2 — viz §6e** (od v0.8 ELEVATED shadow končí).

**Tok:** `FB_Main` po existující validaci (E_PARSE/E_REPO/registr) a před exekucí zavolá `FB_RiskGate`. Čistě čtecí (Č) dávky jdou mimo gate (response nemá `risk`). Zápisová dávka dostane `response.risk = { riskLevel, riskReasons[], metrics{writeOps, createOps, updatedExisting, deleteTargets, affectedElements, affectedPackages, affectedDiagrams, moveOps, metricsComplete}, policyValid, payloadHash, elapsedMs, hashMs }`. BLOCKED → `E_RISK_BLOCKED` (dávka celá `skipped`, soubor do `rejected\`, audit se zapíše — bez auditu nejde ladit limity). Kontrakt `FB_Main(Repository, requestText)` nezměněn.

**Klasifikace** (deterministická, bez AI): třída per operace z `FB_RiskPolicy.classes` (LOW/ELEVATED/BLOCKED, mapa musí pokrývat všech 25 Z operací registru) + prahy `elevate`/`block` nad metrikami + eskalační pravidla v kódu gate (jen eskalují, nikdy nesnižují): `messages` s `rebuild:true`, `operations` s `parameters` (W2a), `elements` update se **změnou** `type` (W2b — shodný type neeskaluje), cizí diagram přes práh `foreignDiagrams`. **B4**: jakýkoli target dávky = konfigurační element bridge (AICodeBridge dle GUID/ID/jména, jména `FB_RiskPolicy`/`FB_OpsAllowed`/`FB_Config`/`FB_ScaffoldConfig` + nad rámec zadání `FB_Whitelist`) → BLOCKED — kryje i create elementu s takovým jménem (dvoudávkový útok, T5-12).

**`$N` pravidlo (B3):** vlastní prvek = jen `$N` na výsledek CREATE větve Z operace. `$N` na výsledek čtecí op nebo update větve = existující target → `updatedExisting`. Nejistota (matchByName/dedupKey, find_or_create, dopředná reference, nerozhodnutelná větev) → fail-closed ELEVATED. Negativní důkaz: dávka -10 (`$0[0]` z `find_elements_by_name` → `updatedExisting: 1`), pozitivní -09 (`$0` na create větev → `updatedExisting: 0`).

**Fail-closed:** repo bez politiky NEBO neúplná mapa classes NEBO chybějící práh = politika nevalidní → vše ELEVATED s důvodem (W9, dávky -14/-15). Neresolvovatelný target → ELEVATED (T5-4, dávka -11). Překročení `budgetMs` → ELEVATED „metriky nespočítány“ (W5). Payload nad `hashMaxChars` → hash se nepočítá, ELEVATED. Pád gate → ELEVATED, nikdy LOW. **W8**: první zápisová dávka po `E_EXCEPTION` v téže session → ELEVATED (in-memory flag, zaniká s reloadem kódu).

**MOVE — revize v0.12.** Původní text zde tvrdil, že `moveOps = 0` je *rezervovaná* metrika a že přesun elementu mezi packages „bridge NEUMÍ a plánovaně nepřibude" (nález N-2). ⛔ **Nepravda:** Automation API přesun umí (`Element.PackageID` + `Update()`), šlo o **nedostavěnou funkci**, ne o hranici protokolu. ## 6e. Risk Gate — confirm okruh (iterace 4b V2, v0.8, dávky 20260819-22…41)

ELEVATED přestává být shadow: **žádný zápis bez lidského potvrzení nad skutečným payloadem** (zadání 4b v1.1 §3 kroky 4–6, §6; dispozice B1/B2/W1/W6 závazné).

**Tok ELEVATED dávky:**

1. `FB_Main` dostane **cestu** k req souboru (kontrakt I5, §1) → jedno binární čtení → SHA-256 surových bajtů (`payloadHash`) i parse z týchž bajtů.
2. Gate klasifikuje ELEVATED → **žádný zápis**. Executor vygeneruje **jednorázový nonce** (`FB_Nonce` — JScript nemá crypto: SHA-256 přes kombinaci času před/po spin-loopu, počtu iterací spin-loopu, 4× `Math.random()` procesu, 2× `FSO.GetTempName()`, payloadHash+id+identita repa, in-memory čítač; obrana nestojí na kryptografické dokonalosti, ale na tom, že hodnota **není odvoditelná z plaintextu dávky** — B2). Req soubor se přesune do `requests\pending\` (beze změny jména), response `confirm_required` nese souhrn (`risk.summary`: počty per op, targety, packages, diagramy), `riskReasons` (vždy konkrétní důvod, CR §12), `hashPrefix` a — **jen v `res-*.json`** — plný `payloadHash` + `nonce`.
3. **Potvrzení = výhradně lokální úkon** přes **`FB_ConfirmPending(Repository, path, nonce, payloadHash, channel, approve)`** — nová operace modelu, která **NENÍ v registru FB_Main** (nedosažitelná obsahem dávky žádného kanálu, B1). Volají ji jen UI adaptéry: popup pumpy (kanál `pumpa`), dialog GUI fallbacku (`gui`), stavové okno vrátného (`okno`, iterace 4). UI čte nonce+hash z res souboru.
4. `FB_ConfirmPending` bezstavově: ověří umístění souboru v `pending\` + nonce a hash **proti res souboru na disku** (nesoulad/chybějící = `E_RISK_CONFIRM`, soubor zůstává v pending\ — nonce se přepisem res „spálí", obnova = vrátit soubor z `pending\` do `requests\` → nová klasifikace s novým nonce) → **přepočte SHA-256 surových bajtů pending souboru** (nesoulad = `E_RISK_INTEGRITY`, nic se neprovede, soubor do `rejected\` + audit — CR §7) → zavolá `FB_Main` nad týmž souborem s in-call confirm kontextem.
5. `FB_Main` při potvrzeném běhu **re-klasifikuje nad aktuálním stavem modelu** (W1 — model-state TOCTOU): nesouhlasí-li metriky s potvrzeným souhrnem, exekuce neproběhne a vzniká **nové `confirm_required` s novým nonce** (soubor zůstává v pending\, UI nabídne nové kolo). Shoda → exekuce; audit nese pole potvrzení (§8). Fresh BLOCKED → `E_RISK_BLOCKED` + rejected\.
6. **Zamítnutí** (Ne/Zrušit v dialogu) → `E_RISK_REJECTED`, soubor do `rejected\`, audit (`confirmedByUser: false`). **Bez rozhodnutí** (Storno/timeout) → dávka dál čeká v `pending\`; pumpa ji znovu nabídne po startu/re-attachi, GUI fallback při každém spuštění.

**Vynucení B1 v executoru:** potvrzovací pole v OBSAHU dávky (top-level `confirm`/`nonce`/`payloadHash`/…, op-level `nonce`/`payloadHash`) = `E_RISK_CONFIRM`, dávka do `rejected\`, nic se neprovede — kryje i soubor podvržený přímo do `requests\` (T5-7). Adapterová pravidla (vrátný, Downloads watcher) zůstávají jen druhou obranou.

**Pravidla §6 zadání:** plný `payloadHash` ani `nonce` nikdy do chat verze (jen `hashPrefix`; hlídá vrátný + copilot-instructions); potvrzení nikdy z transportních kanálů; nonce jednorázový (každý další krok res přepíše). Bezstavovost: žádný in-memory stav gate — potvrzení přežije restart EA i pumpy (T5-14: po restartu EA pumpa dávku v `pending\` znovu nabídla, týž hash).

**Migrace E_QUOTA (W6):** op-level `confirm: true` ztrácí účinek — `FB_Main` pole odstraní a přidá warning do response (stará dávka NEspadne na chybu); klony jdou vždy ELEVATED cestou (třída politiky), `E_QUOTA` se už nevydává. Objem klonu se dál vždy vykazuje (`volume`).

**Kanály potvrzení:** pumpa v0.5 = konzolový souhrn + **popup Ano/Ne/Storno s timeoutem 300 s** (vědomá odchylka od zadání „Enter na konzoli": `StdIn.ReadLine` nemá timeout — nezodpovězené potvrzení by navždy zastavilo watcher včetně LOW dávek; popup po timeoutu nechá dávku čekat a pumpa jede dál; lokálnost úkonu je táž). GUI fallback v0.3 = EA dialog `Session.Prompt` YES/NO/CANCEL (fallback `WScript.Shell.Popup` přes FB_ComObj) + po zpracování `requests\` nabídne i dříve čekající dávky v `pending\`.

**Výkon (T5-9 dokončení):** JScript pumpy — hash 492 kB raw-bytes ≈ 1,3 s (v0.7 měření platí, plus ~stejný čas base64+UTF-8 dekódování); **EA runtime (17.1.5) — hash 492 kB textovou cestou = 63 ms** (JS engine EA je na FB_Sha256 řádově rychlejší než WSH JScript); gate běžných dávek 4–15 ms v obou. Rozpočtová past W5 se tedy týká hlavně pumpy; `hashMaxChars` 2 MB je bezpečný strop.

**E2E důkazy (dávky 20260819-22…41):** viz MATICE-PARITY sekce „Risk Gate confirm okruh V2".

## 6f. Vrátný — AI import režim (iterace 4, v0.9)

Kontinuální odbavování dávek z M365 Copilota **bez pumpy**: jedním kliknutím v EA se zapne, jedním vypne, stav je viditelný ve stavovém okně. EA zůstává mezi dávkami použitelná (HITL review mezi kroky), zamrzlá je jen sekundy během zpracování dávky. Souborový kanon (`requests\`/`responses\`/`pending\`/`processed\`/`rejected\`) i executor (`FB_Main`, confirm okruh §6e) **beze změny** — vrátný je jen nový transportní adaptér + kanál potvrzení `okno`.

**Topologie smyčky (zadání §2, neměnná):** Copilot v prohlížeči vygeneruje dávku → Miloš **Copy** → vrátný (PS proces zrozený inline z EA) zachytí ve schránce signaturu `"protocol":"eafb/` → **okamžitě materializuje** `req-*.json` do `requests\` (fronta žije v souborech, ne ve schránce — W4) → **šťouchne do EA** COM attachem `GetElementsByQuery("FB_Process", "req|<cesta>")` → `FB_Process` (uvnitř EA, plné COM) zavolá `FB_Main` → executor zapíše `res-*.json` → vrátný vloží **chat verzi** (`FB_ChatRender`) do schránky a přepne semafor.

**Komponenty:**

- **`FB_GatekeeperLaunch`** (launcher, menu „Zapnout AI import režim"): vytáhne kanon z `FB_Gatekeeper`, dosadí parametry (`$RepoId`, `$BaseDir`, `$DlDir`, reap časy, `$SessionInfo`), odstraní komentářové řádky a spustí `powershell.exe -NoProfile -STA -WindowStyle Hidden -Command -` s kanonem po **StdIn rouře** (`WScript.Shell.Exec`). **Žádný skript na disku, žádný payload na příkazové řádce.** W8: volá `FB_SessionStart` (otevírací baseline) **před** spuštěním vrátného. Volitelný `<baseDir>\gk-config.json` přepíše časy/`dlDir`/`debug` bez restartu EA (`debug:true` = viditelná konzole PS pro ladění).
- **`FB_Gatekeeper`** (kanon vrátného, PS zdroj jako text): clipboard watcher (**událostní** `AddClipboardFormatListener`, ne polling — W1/R5), materializace req s dedupem (`id` + hash napříč kanály — W5), COM šťouchnutí, chat verze do schránky, **stavové okno** WinForms (always-on-top), **single-instance mutex** (W3) + **reap** osiřelého vrátného. Pin na **Windows PowerShell 5.1** (`GetActiveObject` v PS7 neexistuje — I1).
- **`FB_Process`** (Add-in Search „FB_Process", separátor **TEČKA** — lekce T4-0a): shim v EA runtime (Mozilla JS, COM přes `FB_ComObj`). Příkazy `ping|<token>` (identita repa do `gk-ping-*.json` — ověření W3 §3.3), `req|<cesta>` (FB_Main + res + sidecary + přesuny), `confirm|approve|reject|<pend>|<nonce>|<hash>` (→ `FB_ConfirmPending`, kanál `okno`). **Nikdy nesmí surface UI/modal** (W7) — chyby jen do souboru + Log. Přijímá jen soubor přímo v `requests\` (pending\ a podsložky odmítá — druhá obrana; první je executor E_RISK_CONFIRM).
- **Stavové okno:** semafor **ČEKAM NA DAVKU / ZPRACOVAVAM (nekopíruj) / 🟢 ODPOVED VE SCHRANCE**, čítače (přijato/OK/chyby/potvrzeno/zamítnuto), **seznam fronty + čekajících ELEVATED dávek** (I6 — víc čekajících viditelně), souhrn vybrané dávky (`FB_ConfirmSummary`, bez nonce/plného hashe), tlačítka **Provest / Zamitnout / Ukoncit rezim**. Stavy REATTACHING/REAPING mají vlastní barevnou reprezentaci (W3).
- **Downloads watcher** (sekundární vstup): vzor `ea-req-*.json`, stabilita souboru, dedup podle `id` sdílený se schránkou (W5). Schránka je primární.

**Confirm okruh kanálem `okno` (kontrakt iterace 4):**

1. ELEVATED dávka → `FB_Main` (přes `FB_Process`) vydá `confirm_required`, přesune soubor do `pending\`, `res-*.json` nese `confirm.nonce` + `confirm.payloadHash` (**jen v res**) + `hashPrefix`. Vrátný vygeneruje **sidecar** `res-*.confirm.txt` (souhrn pro okno) a `res-*.chat.txt` (chat ACK — jen `hashPrefix`, počty, důvody; §6.3).
2. Okno zobrazí `CEKA: <soubor>` + souhrn **konkrétní** dávky (id, metriky, targety, důvody). Fronta víc čekajících ELEVATED je viditelná (I6).
3. **Provest/Zamitnout** → vrátný čte `nonce`+`payloadHash` z `res-*.json` a volá `FB_ConfirmPending(Repository, <pending path>, nonce, payloadHash, "okno", approve)`. Zrušit → `E_RISK_REJECTED` (rejected\, audit `confirmedByUser:false`). Bez rozhodnutí → dávka **čeká dál v pending\** (vrátný ji NIKDY neodbavuje sám).
4. Re-klasifikace (W1) může vrátit **nové** `confirm_required` s novým nonce → okno nabídne nové kolo, nikdy neprovádí bez čerstvého potvrzení.
5. Chat ACK do Copilota **nikdy** nenese plný hash ani nonce — jen `confirm.hashPrefix` (12 znaků), počty a důvody (`FB_ChatRender` hlídá; PROTOKOL §6e pravidla, zadání 4b §6.3).

**Nosič kódu (rozhodnutí 2026-08-19, upřesněno 2026-08-20):** `-EncodedCommand` unese ~12 k znaků (Base64 z UTF-16 inflatuje ×2,67 pod strop 32767 — W2/R4), kanon vrátného má ~15,5 k. Místo fallbacku R1 (session mód) se zvolil **StdIn carrier**. Původní varianta (EncodedCommand s bootstrapem `iex([Console]::In.ReadToEnd())`) **narazila na první živé spuštění: Norton `IDP.HELU.CMD.Generic24` „detekce pomocí příkazového řádku" (ochrana na základě chování) zablokoval `powershell.exe`** — base64 blob na příkazové řádce je přesně command-line vzor, na který heuristika kýve (a blokované spuštění pak vrátilo `Exec` = undefined → chyba launcheru). **Oprava:** `powershell.exe … -Command -` — příkazová řádka je **čistá** (žádný payload), celý kanon jde rourou přes StdIn. Drží všechny principy §2 (kanon v modelu, zrození inline z EA, žádný soubor na disku, `powershell.exe` 5.1); mění se jen nosič payloadu (roura místo command line) → bez délkového limitu i bez base64 signatury. **⚠ Chování-based AV/EDR může i tak namítat proti vzoru EA→powershell + čtení schránky (R3/W1)** — to je konkrétní vstup pro R5 (podmínka C-A: DLP/EDR clearance před nasazením). Odchylka od zadání §7/R4 „při překročení = R1" — zapsána i do oznámení R5.

**QC v ACK (§3.4, W6):** po zápisové dávce, která něco zapsala, `FB_QcRun` spustí kontroly z `FB_QcConfig` scopované na dotčené packages (`risk.summary.packages`). **Tři stavy odděleně** od stavu zápisu: `ciste` | `nalez` | `nedobehlo:<důvod>` — selhání QC (např. dialekt SQL) se NIKDY nehlásí jako chyba zápisu (jinak by Copilot přeposlal → duplicity B2). Doba běhu nad reálným EMR se měří v T4-6 (banka).

**Trvalé lekce respektované vrátným:** JScript ES3 (kanon je čistý JS text); COM v EA runtime jen přes `FB_ComObj` (§1a) a binární čtení jen v JScriptu (§1a/4 — FB_Process čte texty utf-8, hash řeší executor); aktivace kódu v EA runtime = **plný restart EA** (menu + FB_Process); `deploy_src` přenačítá pumpu až po doběhnutí dávky; falešné OK `rowCount:0` po odkliku modálu — chat ACK po dlouhém šťouchnutí (`$StuckSec`) přidá varování „ověř kontrolním čtením" (§5a/5).

**E2E:** offline harness (Node mock COM/EA) **49/49 PASS** — syntaxe všech 87 src, FB_ChatRender (10 případů, vč. „nikdy nonce/plný hash" a W10 rozpočtu), FB_QcRun (5 stavů), FB_Process (ping/req/confirm/guard pending\/sidecary/kanál okno), FB_GatekeeperLaunch (StdIn carrier `-Command -` bez base64 na příkazové řádce, parametry, gk-config, debug), PS invarianty kanonu (párování závorek, žádné here-stringy, mutex/reap/kanál okno/druhá obrana/dedup, ASCII). **Reálný PS 5.1 parse + živý klikací E2E provede Miloš** (první živé spuštění 2026-08-20 narazilo na Norton blok `-EncodedCommand` → oprava na `-Command -`, viz nosič kódu výše) (`docs/e2e-iterace4/PROTOKOL-E2E-ITERACE4.md`, dávky 20260820-*).

## 6g. Iterace 5 — autorizace, zvýraznění v browseru, kontext výběru (v0.10)

Rozhodnutí Miloše 2026-08-20 (analytická iterace před stavbou): security off = vše povoleno; read přístup = per-user aktivace add-inu; B = všechny tři varianty (proklik + search + spike); C = klientské předání kontextu.

**(A) Write fíčury add-inu za EA security skupinou.** Vrstvy autorizace (nezaměňovat, viz komentář `FB_AccessGroups`): (1) KDO smí add-in používat = **per-user aktivace** add-inu v EA (Manage Add-Ins; EA nativní, žádný kód bridge; audit aktivací = SQL dotaz správce); (2) KDO smí **write fíčury** = členství v EA security skupině dle `FB_AccessGroups` `{repo, writeGroups[]}` — vynucuje **executor** (`FB_Main`, před Risk Gate) → `E_ADDIN_ACCESS`, jedna mechanika kryje všechny kanály (pumpa/clipboard/GUI/vrátný); (3) KAM smí zapisovat = EA balíčkové skupiny / `@F002_Write` (platí i přes API; bridge jen překládá chybu — `FB_InterpretError`, `E_PERMISSION`/`E_LOCKED`); (4) co smí AI kanál = `FB_OpsAllowed` + od v0.17 blacklist `FB_WriteScope` (§6k; do v0.16 `FB_Whitelist`). `FB_UserAccess`: `Repository.IsSecurityEnabled` (false → „write", vše povoleno) + `GetCurrentLoginUser(false)` + členství SQL `t_secuser` ⋈ `t_secuser_group` ⋈ `t_secgroup` (**⚠ jména tabulek ověřit v bance čtecí dávkou** — zadání zmiňovalo `t_secmember`, standardní schéma má `t_secuser_group`; SQL běží JEN při zapnuté security, na dev .qea se nespustí — lekce §6a/3). Fail-closed: repo bez položky / login nezjištěn / SQL selže → „read" s důvodem. Cache per repo+login na session (změna členství = restart EA). `FB_AccessGroups` přidána mezi B4 chráněné elementy (`FB_RiskGate`).

**Vrstva 1 (aktivace add-inu) — úložiště a audit (SELECT od Miloše, 2026-08-20):** per-user/per-group aktivace in-model add-inů bydlí v **`t_xrefsystem`** — `Type` = `UserSettings` (uživatel) / **`GroupSettings` (skupina!)**, `Client` = `t_secuser.UserID` / `t_secgroup.GroupID`, `Supplier` = `ea_guid` add-in objektu. Existence `GroupSettings` znamená, že správce EA umí aktivaci add-inu řídit i **na úrovni security skupiny** nativně — vrstva 1 tedy není jen individuální opt-in. Audit „kdo má add-in aktivovaný":

```sql
SELECT t_xrefsystem.Type
     , t_secuser.FirstName + ' ' + t_secuser.Surname AS FullName
     , t_secuser.UserLogin
     , t_secgroup.GroupName
     , t_xrefsystem.Client
     , t_xrefsystem.Supplier
     , t_object.Name
FROM ((t_xrefsystem
LEFT JOIN t_secuser  ON t_xrefsystem.Client   = t_secuser.UserID)
LEFT JOIN t_secgroup ON t_xrefsystem.Client   = t_secgroup.GroupID)
LEFT JOIN t_object   ON t_xrefsystem.Supplier = t_object.ea_guid
WHERE t_xrefsystem.Type IN ('UserSettings', 'GroupSettings')
  AND (t_secuser.UserLogin IS NOT NULL OR t_secgroup.GroupName IS NOT NULL)
ORDER BY t_xrefsystem.Supplier, t_xrefsystem.Type, t_xrefsystem.Client
```

(Dialekt: string konkatenace `+` = MS SQL; na SQLite `||`. Potvrzuje i jména tabulek `t_secuser`/`t_secgroup` použitá ve `FB_UserAccess`.)

**Osiřelé aktivace add-inů (N-K8-5, SQL pro správce — od 12. 10. 2026, vlákno Z261004b‑8).** EA po smazání add-inu (elementu) řádky `UserSettings` / `GroupSettings` v `t_xrefsystem` neuklízí; audit výše je odfiltruje JOINem, ale zůstávají v databázi. Výpis osiřelých = `Supplier` bez protějšku v `t_object`. **Tentýž text běží v SQLite i v MS SQL** (žádná konkatenace ani dialektová funkce — proto bez `FullName`):

```sql
SELECT x.Type, x.Client, x.Supplier, u.UserLogin, g.GroupName
FROM t_xrefsystem x
LEFT JOIN t_object   o ON o.ea_guid = x.Supplier
LEFT JOIN t_secuser  u ON u.UserID  = x.Client
```

## 6i. Iterace 6 — join na krok, `move_elements`, internal requirements (v0.12, dávky 20260821-90…A4)

Iterace dostavěla tři věci, které POC odhalil jako chybějící, a **opravila dokumentaci, kterou v0.11 propsala podle špatné diagnózy**.

### A. `join` = návrat do kroku (oprava vyvráceného nálezu N-1)

**Jak nález vznikl a proč obstál celý POC.** Agent v POC poslal `join: "2"` (číslo kroku), dostal warning `join '2' neni v davce`, přečetl si `src/FB_OpScenarios.js`, uviděl `findMade(mdef.join) → ScenarioGUID` a usoudil, že `join` je jméno scénáře. Poslal jméno, warning zmizel, response i readback hlásily GUID — a z toho vznikl závěr „EA neumí návrat na konkrétní krok". Ten závěr se propsal do protokolu v0.11, do kitů pro Copilota i do metodiky. **Nikdo se nepodíval do EA UI.** Když se Miloš podíval (2026-08-21), stálo v Scenarios → Entry Points u **všech** větví obou UC `Join = End`. Zápis, který response označila za úspěšný, EA ignorovala.

**Poučení, které je obecnější než `join`:** zelený readback dokazuje jen to, že se **naše** hodnota uložila tam, kam jsme ji zapsali — nedokazuje, že jí **EA rozumí**. Čtení vlastního zdrojáku není důkaz o chování hostitele. U každé vlastnosti, kterou EA renderuje ve svém UI, je jediný přijatelný důkaz **pohled do toho UI**, nebo diff proti stavu, který v UI vyrobil člověk.

**Postup reverse engineeringu** (opakovatelný recept pro další „EA formáty"):

1. čtecí dávka **PŘED** — `SELECT * FROM t_objectscenarios WHERE Object_ID = …` (dávka -91; `SELECT *` kvůli lekci §6a/3, schéma přes `sqlite_master` kvůli N-4);
2. **člověk** nastaví hodnotu v EA UI (zde: dvě větve UC-95002 → `Join` 7 a 10) — přesná instrukce kam kliknout je součást zadání;
3. čtecí dávka **PO** (dávka -92), diff.

**Výsledek diffu — formát:**

```xml
<step name="Člen zrušení potvrdí." guid="{D628F1CC-…}" level="6" … trigger="1" link="">
    <extension level="6a" guid="{309D3DEA-…}" join="{631910FC-…}"/>
</step>
<step name="Systém zruší rezervaci a uvolní kapacitu lekce." guid="{631910FC-…}" level="7" …/>
```

- `<extension>` `guid` = **ScenarioGUID větve** (beze změny proti v0.4);
- `join` = **GUID KROKU**, do kterého se tok vrací, nebo doslovný řetězec **`"End"`**;
- větev, u které člověk `Join` nesahal, EA při uložení normalizovala z `join=""` **na `join="End"`**; hodnotu `ScenarioGUID` (co tam psal starý bridge) EA rovněž zahodila do `End` — proto to celou dobu vypadalo „prázdně", ne „chybně".

### B. `move_elements` — přesun mezi packages

**Tvar (rozhodnutí Miloš 2026-08-21): samostatná operace, ne pole `package` v update větvi.** Zamítnutá varianta „respektovat `package` u updatu" je pohodlnější pro klienta, ale dávky běžně nesou `package` u updatu jen popisně — strukturální přesun jako vedlejší efekt běžné update dávky je přesně to riziko, které se tady nechce. `package` v update větvi proto **zůstává bez účinku a nově vrací warning** s odkazem na `move_elements` (konec falešného OK, N-2).

**Risk Gate: ELEVATED vždy**, i pro jediný prvek. Důvody (plné znění v `FB_RiskPolicy`): je to zásah do *struktury*, ne do obsahu prvku; není vratný opakováním dávky (původní package v dávce není); governance visí na package (`SA-Status`, P1), takže přesun mění, jaký stav a jaká brána na prvek platí; metodika P3 přesun mezi pracovním prostorem a ostrou větví výslovně svěřuje člověku. Metrika `moveOps` je nově skutečná; volitelný práh `elevate.moveOps` politiku neznevaliduje, když chybí (jinak by nový práh fail-closed shodil každou dříve nasazenou politiku do ELEVATED).

**⚠ Lekce z živého testu (dávka -A1): EA si přesun vlastněných potomků kaskáduje sama.** Po `Element.PackageID = X; Update()` mají child elementy (`ParentID`) nové `Package_ID` bez našeho zásahu. Dokázáno čtením **uprostřed** dávky: UC-95003 šel 1070 → 1067 a zpět, jeho 4 BRU šly s ním, a náš průchod přitom neměl co opravovat. To vyrobilo zavádějící `children: 0` — číslo, které se dá číst jako „potomci zůstali vzadu". Response proto od v0.12 nese **dvě čísla**: `children`/`diagrams` = kolik vlastněných prvků s rodičem šlo, `childrenFixed`/`diagramsFixed` = kolik z nich musel dorovnat bridge. `withChildren: false` vypíná **jen náš průchod** — kaskádu EA vypnout nelze. U diagramů vlastněných elementem kaskáda EA **ověřena není** (v testovací větvi žádný takový diagram nebyl), tam je průchod skutečná pojistka.

**v0.22 (N‑RE‑17, 15. 10. 2026): cíl `owningElement` — přesun pod prvek.** Metodický důvod (Miloš 15. 10.): rozhraní patří pod komponentu (výjimka = rozhraní vedená samostatně v `Solution Artefacts Proposed`), prvky sekvence (lifeliny, refy, gaty) pod prvek SR/UCR na úroveň jeho kompozitního diagramu. Bridge nastaví `Element.ParentID` = vlastník a `PackageID` = balíček vlastníka, potomci a vlastněné diagramy jdou stejnou kaskádou jako u balíčku; `package` a `owningElement` současně = `E_ARGS`, vlastník = sám prvek nebo jeho potomek (cyklus) = `E_ARGS`; Risk Gate: třída ELEVATED trvá, balíček vlastníka se počítá, okno říká „PRESUNOUT N prvků pod jiný prvek ve stromu (…)“. **Lekce EA Automation:** zápis `PackageID` (i na stejnou hodnotu) EA bere jako přesun do balíčku a `ParentID` při `Update` **vynuluje** (`Update` přitom vrátí true) — proto bridge zapisuje `PackageID` jen při změně a `ParentID` ve vlastním `Update`, po něm **readback** `GetElementByID(...).ParentID` (nesoulad = `E_EXCEPTION` „EA nezapsal vlastnika“). Živě: 14 rozhraní pod komponenty (jeden balíček), 56 lifelin/refů/gatů pod 4 SR + 9 UCR (3 dávky, ruční baseline nad společným předkem stačí). Baseline politika: cíl = balíček vlastníka (`volumeUnknown` trvá).

**Metodická past, na kterou se přišlo mimochodem:** první ostrá move dávka (-97) vrátila `moved: false` — oba UC už v cílových packages byly, protože je mezitím někdo přesunul ručně. Doporučený vzor pro živé testy operací, které mění stav do cílové podoby.

### C. `create_or_update_requirements` — internal requirements (lokální BRU dle U5)

Metodika ITAN od revize **U5 (2026-08-21)** drží **lokální** pravidla `BRU<čísloUC>-Y` jako **internal requirement uvnitř UC** (Responsibilities → Requirements, `t_objectrequires`), ne jako samostatný element pod UC s `Usage` konektorem — dřívější N-K3-2 je pro ně překonané. Je to stejný pohyb jako U2 (scénáře → Scenarios tab) a PRE/PST/ASU (→ Constraints tab). **Přepoužitelná** `BRU-####` zůstávají elementem v `RULES (REUSABLE)` + `Usage` — ta se touto operací nepíšou.

Mechanika: `Element.Requirements.AddNew(name, type)` + `Notes`/`Status`/`Priority`/`Difficulty`/`Stability` + `Update()`. Requirement **nemá GUID** (tabulka má jen umělé `ReqID AUTOINCREMENT`) — identita = `(Object_ID, jméno)`, přesně jako u constraintů. Sloupce ověřeny sondou `sqlite_master` (dávka -93, lekce N-4): `ReqID, Object_ID, Requirement, ReqType, Status, Notes, Stability, Difficulty, Priority, LastUpdate`. `ReqType` se **nevaliduje proti výčtu** (na rozdíl od constraintů) — seznam typů je v EA konfigurovatelný; default `Functional`. Update = deterministický rebuild V2d (smaž vše + zapiš v pořadí dávky, `removed` v response), validace celé dávky **před** prvním mazáním.

**Živě ověřeno** (dávka -A4, UI potvrzeno Milošem): 7 lokálních BRU obou UC převedeno z elementů na internal requirements (3 + 4), původní BRU elementy smazány, jejich 7 `Usage` konektorů zaniklo s nimi (`ZbyleUsageKonektory: 0`), QC čisté. Tím se rovnou uklidil dluh POC: UC-95002/95003 i jejich obsah teď leží ve svých packages 1069/1070.

**Implicitní ochrana (vždy, i s prázdným blacklistem):** balíček auditu (`FB_Config.auditPkg` — povinný) a balíček, ve kterém leží element `AICodeBridge` (jiné `JavascriptAddin` elementy vedle něj jsou v pořádku; cizí typ prvku nebo podbalíček = vada konfigurace) — obě dědičně na podstrom; kořeny modelu jen jako **uzel** (B1, O5 = a): smazání `E_ARGS`, přejmenování/update `E_BLACKLIST`, nový balíček přímo pod kořenem = důvod okna „Nový balíček … přímo pod kořenem modelu" (ELEVATED); konfigurační elementy podle jména (B4) beze změny.

**Kontrola cíle** (`FB_ScopeCheck` jádro; `FB_CheckWrite` pro balíček se stejnou signaturou jako dřív — ≈ 50 volajících míst beze změny; `FB_CheckWriteEl` pro prvek/diagram): po ose balíčků (`ParentID`, strop 60) **a** po ose vlastníků prvku (I14 — prvek vlastněný chráněným prvkem je chráněný, i když leží ve volném balíčku). Kde: **předem** v předběžné kontrole P2 (`FB_ScopePrecheck`, fáze `targets`, po kontrole přístupu `E_ADDIN_ACCESS`) nad všemi cíli dohledatelnými před provedením (GUID, ID, jméno, cesta, `owningElement`, `dedupKey`, `baselineRoot`; `$N` až při provedení) — jediný zakázaný cíl = dávka se neprovede vůbec, ani záloha, soubor do `rejected\`, audit ano (FB-CZ-08); **při provedení** druhá obrana nad skutečným objektem, i dohledaným přes `dedupKey`/`match`/`matchByName`/`$N` (FB-CZ-09).

**Operace přes hranici** (kap. 5.5 zadání): mazání balíčku, jehož podstrom obsahuje chráněnou větev → `E_BLACKLIST`; přesun — zdroj, cíl i vlastněné podřízené prvky a diagramy (podstrom po úrovních, strop 60 úrovní / 5000 uzlů); klony — **zdroj vždy** (W5: `Element.Clone()` zapisuje klon vedle zdroje), klon kořene odmítnut; diagramy — chráněný prvek smí ležet na volném diagramu (mění se jen diagram), chráněný diagram = `E_BLACKLIST`; `apply_classifier_stereotypes` na chráněný prvek = `E_BLACKLIST`; úklid automatických baselines vynechá a vykáže kandidáty v chráněných balíčcích (`protected: N`, W1).

**Vazby a zprávy — pravidlo „oba konce"** (rozhodnutí Miloše 12. 10. 2026, nahrazuje „vazbu vlastní zdroj" z B2): vazba (i zpráva sekvence) je chráněná, **jen když jsou oba její konce v chráněné části** — s jedním koncem venku chráněná není, ať vede kterýmkoli směrem: založit, změnit i smazat ji lze. Kontrola běží nad **skutečnými konci** dohledaného konektoru (guid, `dedupKey`, `match`) a při přesměrování nad **novým párem konců**; `allowIncomingRefs: false` navíc zakáže novou vazbu (a přesměrování cíle) z volné části do té větve. `rebuild` u zpráv blokuje jen zprávu s oběma konci v chráněné části. **Zámky EA a vazby (FB-CZ-22, živě 12. 10.):** skupinový zámek balíčku přes Automation hlídá prvky (založení `E_PERMISSION`, změna `E_LOCKED`), ale **vazby vůbec** — vazba ze zamčeného prvku i do něj vznikne, dá se přejmenovat i smazat; bridge zámky u vazeb **nekontroluje** („směr vazby je dán logikou řešení, ne vlastnictvím"). Agent to ví z `writeScope.agentNotes`.

**Kaskády mazání do chráněné části (W2; rozhodnutí Miloše 12. 10. 2026, varianta c):** EA při smazání prvku odstraní prvek ze všech diagramů (i chráněných) a instancím, jejichž je klasifikátorem, nastaví `Classifier = 0` (živě Z10-13 — i v chráněné části). Obě kaskády (b: objekt leží na chráněném diagramu, c: objekt je klasifikátorem chráněné instance) se počítají **už v předběžné kontrole** (`FB_ScopePrecheck.cascadeCheck`, totéž SQL jako `FB_OpDelete.cascade`) nad prvkem i nad obsahem podstromu mazaného balíčku: `cascadeDelete: "block"` → `E_BLACKLIST` v P2 (`problems[].cascade`, `count`, `items[]`); `"allow"` → dávka projde s **důrazným varováním**: `cascades[]` v odpovědi, `risk.cascades[]` + důvod okna (dávka nikdy není LOW) a blok `POZOR - smazani sahne kaskadou EA do CHRANENE casti (zaloha ji nekryje)` s výčtem diagramů/instancí v potvrzovacím okně (`FB_ConfirmSummary`) — člověk rozhoduje s informací; při provedení `warnings[]`. Kaskáda (a) „příchozí vazba s chráněným zdrojem" už **není** zásahem do chráněné části (pravidlo „oba konce").

**Adresace cíle.** GUID a ID beze změny. **Cesta** `{ "path": ["Model", "Oblast", "Balík"] }` od kořene nebo `{ "path": […], "from": "{GUID}" | id | "$N" }` od balíčku — všude, kde operace bere odkaz na balíček; jména se porovnávají **přesně v JS** (SQL jen předfiltr; SQLite vs. MS SQL kolace — W7); víc sourozenců = `E_AMBIGUOUS` s `candidates[]`, chybějící úroveň = `E_NOT_FOUND` s `found` + `children[]`; cesta jen k balíčku (prvek GUIDem, ID, jménem v balíčku nebo výběrem). **Jméno** v zápisové operaci musí odpovídat právě jednomu objektu (jinak `E_AMBIGUOUS`); jména se dohledávají **v P2 před provedením** → na prvek založený dřívější operací téže dávky odkazuj `$N`. Odpověď nese `resolved[] {op, path, ref, kind, guid, id, fullPath}` ke každému odkazu zadanému jménem nebo cestou (FB-CZ-18); okno a ACK ukazují plnou cestu. **Výběr ve stromu** zůstává na agentovi (rozhodnutí 20. 8. 2026, O6 = a): pumpa → `get_selected_context` s `writeCheck{ok, code, note}`; schránka → menu **Kontext vyberu do schranky (pro Copilota)** (§6g/C).

**Záloha bez whitelistu (B3, §6j):** vždy nad konkrétním cílovým balíčkem zápisu (vazba podle zdrojového balíčku); `coveredBy` hledá ruční baseline až ke kořeni modelu; konce konektoru dle guid/ID se dohledají jedním SELECT (rozsah známý); `$N` na update větev → balíček předchozí operace; zbylý neznámý rozsah → naváděná cesta nad **nejbližším společným předkem** dohledaných cílů nebo nad `baselineRoot` z dávky (`E_NO_BASELINE` jen destruktivní podtřída); mazání balíčku: záloha nad rodičem jen když projde velikostní sondou (i ve stínovém režimu), jinak nad mazaným balíčkem + varování (`parentOverThreshold`, T6-28); `sessionBaseline: "auto"` se chová jako `"off"`.

**Hlášení (v0.17, FB-CZ-27):** jedna lidská věta (`FB_ScopeText`) — start session (konzole pumpy), menu *Stav bridge* a ping `writeScope.summary` říkají totéž: `Zapis: blacklist (N chranenych vetvi) | EA security zapnuta/vypnuta | chraneno: <cesty> [note] | bridge chrani i sam sebe: <cesty> | kaskady mazani do chranene casti: …`; ping navíc `writeScope.agentNotes[]` (pravidla pro kit: kam psát + „Zapíšu do:", `E_BLACKLIST` neopakovat, vazby „oba konce", zámky EA vazby nehlídají, `$N` místo jmen, kaskády); chat ACK segment `zapis: blacklist (…)` místo `whitelist:`; `E_BLACKLIST` vždy s plnou cestou cíle, chráněnou větví a `note` (FB-CZ-28); `E_PERMISSION`/`E_LOCKED` s výčtem položek, které proběhly (`items` + `partial: true`, W3).

**Nestaví se:** zóna bez potvrzení `autoZone` (O7 = b — návrh zůstává v zadání kap. 5.10), `requireSecurity`/`E_SECURITY_OFF` (O2 = b), spike předpovědi zámků (O10 = b), dodatek R5 (O8 = b), `"package": "selected"` na executoru (FB-UX-31), cesta k prvku, `mkdir -p` pro cestu.

**Nasazení:** doma `deploy_src` pumpou (nové soubory: `FB_WriteScope`, `FB_WriteScopeCfg`, `FB_ScopeCheck`, `FB_ScopePrecheck`, `FB_CheckWriteEl`, `FB_ResolvePath`, `FB_ResolveFail`, `FB_ScopeText`, `FB_ClipboardContext`; nová položka menu = plný restart EA); v bance bootstrap s položkou `FB_WriteScope` připravenou správcem (`NAVOD-NASAZENI-KLIKACI.md` v1.3 kap. 5.2, 6.3, 7.3a–d). `diff-signatures v0.14 HEAD`: 4 změněné signatury existujících operací (`FB_ResolveEl`/`FB_ResolvePkg` +`mode`, `FB_RiskNote`/`FB_RiskAuditTags` +`baseline`), vše přes `typeof`.

## 8. Bezpečnostní výbava (povinná, ne volitelná)

1. **Hranice zápisu = EA security + blacklist** (`FB_WriteScope`, **od v0.17 místo whitelistu**, §6k): `{repo, cascadeDelete, blacklist:[{pkg:"{GUID}", name, note, allowIncomingRefs?}]}` — zápis projde jen při shodě repozitáře (dle `FB_RepoId`, jinak `E_REPO`), **mimo** chráněné větve (blacklist dědičně na podstrom + implicitně balíček auditu a balíček add-inu; kořeny jen jako uzel) a tam, kam uživatele pustí EA security (`E_PERMISSION`/`E_LOCKED` — bridge ji nekontroluje, O2 = b). Konfigurace se kontroluje při startu, pingu a každé zápisové dávce (`E_SCOPE_CONFIG`). *(Do v0.16: whitelist packages = celá větev `FB_Whitelist {repo, pkg}`, zápis jen uvnitř ní — `E_WHITELIST`.)*
2. **Whitelist OPERACÍ `FB_OpsAllowed`** (nové v 0.2, K4 — náhrada MCP `-enableDelete`/`-enableEdit`): per repo `{repo, allow[], deny[]}`; deny má přednost, `"*"` v allow = vše; čtecí operace povoleny vždy; **repo bez položky = žádný zápis (fail-secure)**. Změna = změna kódu v modelu = baselinovaná událost.
   **Doporučená bankovní konfigurace (P1, §12a+§12g):**
   ```
   { repo: "<TEST-DB>", allow: ["*"],
     deny: ["delete_from_model", "delete_taggedvalue_from_model",
            "remove_elements_from_diagram", "clone_package", "clone_elements",
            "deploy_src"] }
   ```
   (delete/clone se zapínají až v P2+ po zácviku; `deploy_src` je VÝHRADNĚ dev operace — v bance deny trvale.)
3. **Deklarace `repo` v dávce** — kryje směr „dávka pro TEST zpracovaná v PROD".
4. **Baseline politika (§6j, od v0.15):** executor pořizuje **automatickou mikro-baseline nejbližší vlastnící package těsně před první zápisovou operací** dávky, která mění nebo maže existující obsah (čistý create zálohu nepotřebuje); bez pre-image se nezapisuje (`E_NO_BASELINE` / naváděná cesta). *(Do v0.13 zde stálo „auto-baseline whitelistovaných packages při startu session pumpy“ — to od v0.15 neplatí: session baseline je jen doplněk na dev stanici, `sessionBaseline: "auto"`, v bance `"off"`.)* Explicitní pojmenovaná `create_baseline` zůstává (§12c), jméno nesmí začínat `FB-AUTO`. **Auto-baseline záměrně NEpodléhá `FB_OpsAllowed`** (bod 2): není to operace dávky, ale obrana executoru — kdyby správce zakázal `create_baseline`, explicitní baseline neprojde, automatická ano; zákaz obrany by znamenal tichý zápis bez pre-image. `FB_CheckWrite` (od v0.17 kontrola cíle — blacklist, §6k) pro ni platí stejně jako pro explicitní.
5. **Audit**: každá dávka = Artifact `FB <id>` v `#AI-LOG` (tagy `ai.channel=eafb`, `ai.request`); každý zapsaný element nese `ai.channel`/`ai.request`. **Tvar Notes od v0.21 (FB-UI-06, Z261004b-12, 2026-10-12):** tři části oddělené prázdným řádkem a nadpisem —
   ```
   Davka <id> skoncila USPESNE|CHYBOU: N z M operaci provedeno.        ← věty pro člověka (FB_AuditText)
   Uroven rizika: bez potvrzeni | vyzadovala potvrzeni | blokovano. [Potvrdil|Zamitl uzivatel v okne pumpy|dialogu EA <datum cas>.]
   Proc potvrzeni: <věty z FB_ReasonText, ne kódy>            (jen u ELEVATED/BLOCKED)
   Zaloha: '<jmeno>' nad balickem <cesta> | neporizovala se (<duvod>) | nepodarilo se ji poridit (<duvod>).
   Kontrola kvality: ciste (N kontrol, bez nalezu) | NALEZ - <popis> (<id>, Nx) … | neprobehla: <duvod> | bez kontrol - <duvod>.

   --- strojovy zaznam (beze zmeny) ---
   <summary = status: N ops (ok, chyb) + FB_RiskNote — DOSLOVA, beze změny tvaru>

   --- request ---
   <celý text dávky>
   ```
   U odmítnutých dávek (`E_BLACKLIST` a další kódy předběžné kontroly, `E_ADDIN_ACCESS`, `E_RISK_BLOCKED`, `E_NO_BASELINE`, `E_RISK_REJECTED`, `E_RISK_INTEGRITY`) první věta říká, že dávka byla ODMÍTNUTA / ZABLOKOVÁNA / ZAMÍTNUTA a proč, plus „Nic se nezapsalo." **Tag `result` = prvních 250 znaků STROJOVÉHO záznamu, ne vět** (hledání, kalibrace a harness se o něj opírají); tag `ai.risk.codes` nese kódy důvodů. Konečný audit se skládá až **po** kontrole kvality (`FB_QcRun`), proto věta „Kontrola kvality" odpovídá `resp.qc`. Volající bez pátého parametru `human` (signatura z modelu před v0.21) dostane Notes v původním tvaru (strojový záznam + request) — `FB_Audit` čte `human` jen přes `typeof` (kap. 11). Strojový řádek se **nikdy neuklízí jako duplicita** — hlídá ho harness (UI-06 a). Výsledek kontroly kvality jde slovy i do **Output tabu** (jeden řádek za blokem změn, u nálezu až 3 prvky s markerem `(el:ID)`) a do dialogu schránky / GUI fallbacku (FB-UI-11); chat ACK (`FB_ChatRender`) se nemění — ten čte model.
6. **Kvóty klonování — od v0.8 pod Risk Gate** (migrace W6, §6e): objem se vykazuje vždy (`volume`); klony jsou třídou politiky ELEVATED → potvrzení člověka nad skutečným payloadem. `confirm: true` v dávce ztratil účinek (warning); `E_QUOTA` se nevydává.
7. **Risk Gate** (v0.7 výpočet §6d + v0.8 confirm okruh §6e): deterministické metriky + klasifikace každé zápisové dávky (`FB_RiskGate` + politika `FB_RiskPolicy` per repo, fail-closed W9); BLOCKED = `E_RISK_BLOCKED` vč. ochrany konfiguračních elementů bridge (B4); **ELEVATED = vynucené lidské potvrzení** (nonce jen v res, `pending\`, `E_RISK_INTEGRITY`, bezstavová re-klasifikace W1); LOW = auto (B1-A trvá). Potvrzení výhradně `FB_ConfirmPending` (mimo registr operací); potvrzovací pole v obsahu dávky odmítá executor (`E_RISK_CONFIRM`, B1).

## 9b. Clipboard režim — plně ruční fallback bez PowerShellu (v0.9, 2026-08-20)

Vznikl jako reakce na to, že vrátný (persistentní `powershell.exe` hlídající schránku ve smyčce) je pro AV **Dropper** (Norton `CMD:Powershell-AP [Drp]`, Auto-Protect — infostealer signatura, red team W1; potvrzeno naživo 2026-08-20). Rozdíl proti produkčnímu precedentu (JIRA formulář): tamní powershell dělá krátkou bounded úlohu a skončí; vrátný je dlouhoběžící clipboard watcher — jiná třída chování.

**`FB_ClipboardImport`** (menu „Zpracuj davku ze schranky"): běží **celý uvnitř EA.exe, žádný powershell, žádný watcher** → pro AV neviditelné. Na klik přečte dávku ze schránky zevnitř EA (COM `htmlfile` → `clipboardData.getData`), zdedupuje (id+hash, W5), odmítne obsah s potvrzovacími poli (druhá obrana B1), materializuje `req-*.json`, zavolá `FB_Main` (kontrakt I5, cesta) a chat verzi (`FB_ChatRender`) vloží zpět do schránky (`clipboardData.setData`) + ukáže v EA dialogu. ELEVATED dávka → EA dialog Ano/Ne/Storno → `FB_ConfirmPending` **kanál `gui`** (confirm okruh §6e beze změny). UX: Copy → klik → Ctrl+V; klik za dávku (jako M365-A), ale s pohodlím schránky. Registr operací beze změny (menu-only, mimo `REG`).

Vztah k ostatním režimům: **AI import režim (vrátný)** = plně automatický, ale AV-optika (R3/W1 → R5 C-A); **clipboard režim** = klik za dávku, AV-neviditelné, Copy/Ctrl+V pohodlí; **Process requests (File Bridge)** = klik za dávku, dávka jako soubor v `requests\` (žádná schránka). Poslední dva běží uvnitř EA a nevyžadují powershell — vhodné, kde AV/EDR blokuje vrátného.

**✅ Ověřeno naživo 2026-08-20 (eaexample, EA 17.1.5):** clipboard režim E2E funkční — dávky `20260820-c1`/`c2` (ping) přes Copy → menu → `EAFB OK …: 1/1 ops`, dedup W5 potvrzen (druhý klik téže dávky přeskočen). **⚠ NOVÁ DUAL-RUNTIME LEKCE (§1a rodina): `htmlfile.clipboardData.getData` v EA runtime FUNGUJE, ale `setData` TISE nic nezapíše** (schránka drží původní obsah, žádná výjimka — falešné „zapsáno"). Čtení schránky zevnitř EA je tedy OK; zápis zpět řeší `FB_ClipboardImport` přes **read-back ověření + fallback `clip.exe`** (temp UTF-16LE → `cmd /c clip < temp`; `cmd`+`clip` není malware vzor, na rozdíl od powershellu). Odpověď se navíc vždy ukáže v EA dialogu (nezávisle na schránce).

## 10. SQL dialekty

`query` běží v dialektu připojeného repozitáře: lokální `.qea` = SQLite, bankovní repozitář = MS SQL 2022. Executor SQL jen provádí — dialekt hlídá autor dotazu (skilly / copilot-instructions / ea-sql-expert).

**Strop řádků `maxRows` (v0.20, FB-PU-31 / N-B-3, Z261004b-7) — co chrání a co ne.** `op.maxRows` (výchozí 500, nejvýš 5000; neplatná hodnota = výchozí, větší = strop + warning) ořízne `rows[]` v odpovědi; odpověď pak nese `truncated: true`, `rowCount` = **skutečný** počet řádků a `maxRows` = použitý strop. Strop **chrání velikost `res-<id>.json` a kontext agenta — ne dobu běhu v EA.** `Repository.SQLQuery` vrátí bridge až hotové XML celého výsledku; nad velkou tabulkou EA sestavuje minuty a pumpa stojí na `Zpracovavam`, ať je `maxRows` jakýkoli. Dobu běhu chrání jedině **`TOP N` (MS SQL) / `LIMIT N` (SQLite) nebo selektivní `WHERE`** v dotazu samém. Proto bridge dotaz bez `TOP`/`LIMIT`/`WHERE` (a bez agregace) nad známou velkou tabulkou **odmítne** (`E_SQL_UNBOUNDED`, §7) a nad ostatními tabulkami ho pustí s warningem „dotaz bez omezeni“. Seznam velkých tabulek je v kódu `FB_OpQuery` (`BIG_TABLES`) — obecné názvy tabulek EA, žádné řády řádků konkrétního repozitáře; řády patří do kontextu repozitáře (`EA-Repozitar-Kontext(-banka).md`). Pojistka „jen čtení“ od v0.20 odmítá i `;` a `INTO` mimo řetězcový literál (`E_SQL_READONLY`).

**Jak si ověřit názvy sloupců, než dotaz odešleš** (nález N-4, POC 2026-08-21 — pravidlo „ověř si sloupce" existovalo, ale bez nástroje). Neznámý sloupec v EA **nevrátí chybu** — otevře modální dialog, pumpa/vrátný visí do odkliknutí (§6b lekce, `Method_ID` vs `OperationID`) a po zotavení hrozí **falešná nula** (§5a/5). **Od v0.13 (N2 E2E VS Code 2026-09-07) platí pro operaci `query`:** chybný SQL vrací `error`/**`E_SQL`** (§7); **dialog se otevře dál** — `SuppressEADialogs` ho živě nepotlačil (8. 9.), pumpa stojí do kliknutí OK. Pravidlo „ověř si sloupce" tedy zůstává **hlavní obranou** (stojí to dávku i klik u stroje); `E_SQL` odstraňuje jen falešnou nulu. Interní dotazy ostatních operací (`FB_ResolveEl`, `FB_OpDelete`, …) obal nemají — jsou to dotazy s pevnými, ověřenými sloupci.

- **SQLite (`.qea`)** — schéma tabulky bezpečně:
  `SELECT sql FROM sqlite_master WHERE type='table' AND name='t_objectscenarios';`
  (`sqlite_master` je vždy přítomná, dotaz nemůže narazit na neznámý sloupec cílové tabulky). Alternativa `PRAGMA table_info(...)` přes `query` **nechodí** — není to SELECT (`E_SQL_READONLY`).
- **MS SQL (banka)**:
  `SELECT COLUMN_NAME, DATA_TYPE FROM INFORMATION_SCHEMA.COLUMNS WHERE TABLE_NAME = 't_object' ORDER BY ORDINAL_POSITION;`
- **`SELECT *` jako první krok** na neznámé tabulce (vzor §6c u `t_objectconstraint`) — levné, bezpečné a rovnou ukáže jména sloupců.
- **Kvótování rezervovaných slov a jmen s mezerou**: SQLite `"Sloupec"` (dvojité uvozovky) nebo `[Sloupec]`; MS SQL `[Sloupec]`. Řetězcový literál je v obou dialektech `'text'`, apostrof uvnitř se zdvojuje (`''`).
- **Výčet baselines (Baseline politika §6j; doma doloženo spikem 7. 9., SQLite):** `SELECT d.DocID, d.ElementID, d.Version, d.DocDate, d.DocName FROM t_document d WHERE d.DocType = 'Baseline'` — `DocID` = GUID baseline (totéž co `guid` z `GetBaselines`), `ElementID` = GUID package, `Version` = jméno baseline, `DocDate` = ISO `RRRR-MM-DD hh:mm:ss`. Tentýž tvar běží na MS SQL beze změny (žádná dialektová funkce), **ale sloupce je nutné v bance před prvním úklidem ověřit** (`docs/baseline-spike/sql-banka.md` B1/B2). Interní dotazy politiky (`FB_BaselinePolicy`, `FB_SubtreeCount`, `FB_BaselineDecide`, `FB_BaselineCleanup`) používají jen standardní sloupce `t_object`, `t_package`, `t_diagram`, `t_diagramobjects`, `t_connector`, `t_attribute`, `t_operation`, `t_objectproperties`, `t_connectortag`, `t_document`.
- **Falešná nula**: `rowCount: 0` znamená vždy jen „dotaz nic nevrátil", **nikdy** „data neexistují" — zvlášť po zotavení z modálu (od v0.13 selhaný SQL u `query` končí `E_SQL`, nula je tedy s vysokou pravděpodobností pravá; pravidlo kontrolního čtení platí dál). Kontrolní čtení pak vždy v **čerstvé dávce** (§5a/5); chat ACK to u nulového výsledku říká výslovně.

### 11a. Kalibrace potvrzovacích oken (KONCEPCE pravidlo 9; od 12. 10. 2026, vlákno Z261004b‑8)

Audit (`#AI-LOG`, Artifact `FB <id>`, §8 bod 5) nese u každé zápisové dávky tagy: `ai.risk.level` (LOW / ELEVATED / BLOCKED), `ai.risk.reasons` (technický text důvodů, ořez 250 znaků), **`ai.risk.codes`** (od v0.19: stabilní kódy důvodů oddělené `;`, např. `CLASS_ELEVATED;THRESHOLD_ELEVATED` — tabulka kódů a vět = `src/AICodeBridge.FB_ReasonText.js`), `ai.risk.metrics` (`writeOps=…;updatedExisting=…;affectedPackages=…`) a `ai.risk.confirm` (`required=0|1;confirmedByUser=0|1;channel=pumpa|okno|…|expired;at=<čas>`). **Kalibrace seskupuje podle kódů, ne podle textu** — texty vět se smí měnit, kódy ne.

**Kdy:** po **4 týdnech** používání (doma i v bance zvlášť — každé prostředí má svou politiku), pak vždy 4 týdny po poslední změně politiky. Audity před v0.19 (do 12. 10. 2026) kódy nemají a dotazy je vynechají.

**Čtecí dávka (souhrn).** Funguje beze změny v SQLite i MS SQL (selektivní `WHERE` nad balíčkem auditu místo `TOP` — SQLite `TOP` nezná; žádná konkatenace, `CASE` + `LIKE` jsou v obou dialektech). `<GUID-AILOG>` = GUID balíčku auditu (`FB_Config.auditPkg`, ping `writeScope.implicit[kind=audit]`); v bance dosadí `tools\banka-dosad.cmd`, vzor `docs/e2e-banka/ready/req-banka-kalibrace-oken.json` (oba dotazy ověřeny nad syntetickou SQLite databází 12. 10. 2026 — hranice kódů, čtyři stavy okna; MS SQL čeká na první kalibraci v bance):

```sql
SELECT q.uroven, q.kody, q.okno, COUNT(*) AS davek
FROM (SELECT l.Value AS uroven, r.Value AS kody,
             CASE WHEN c.Value IS NULL THEN 'bez zaznamu'
                  WHEN c.Value LIKE 'required=0%' THEN 'bez okna'
                  WHEN c.Value LIKE '%confirmedByUser=1%' THEN 'potvrzeno'
                  WHEN c.Value LIKE '%channel=expired%' THEN 'vyprselo'
                  ELSE 'zamitnuto' END AS okno
      FROM t_object a
      INNER JOIN t_objectproperties r ON r.Object_ID = a.Object_ID AND r.Property = 'ai.risk.codes'
      LEFT JOIN t_objectproperties l ON l.Object_ID = a.Object_ID AND l.Property = 'ai.risk.level'
      LEFT JOIN t_objectproperties c ON c.Object_ID = a.Object_ID AND c.Property = 'ai.risk.confirm'
      WHERE a.Package_ID IN (SELECT Package_ID FROM t_package WHERE ea_guid = '<GUID-AILOG>')
        AND a.Object_Type = 'Artifact') q
GROUP BY q.uroven, q.kody, q.okno
ORDER BY q.kody, q.okno
```

**Detail jednoho kódu** (kombinace s více kódy rozpadne; `<KOD>` = kód z tabulky; čtyři varianty `LIKE` drží hranici `;`, takže `CLASS_ELEVATED` nechytí `CLASS_ELEVATED_FOREIGN`):

```sql
SELECT a.Name AS davka, a.CreatedDate AS kdy, r.Value AS kody, m.Value AS metriky, c.Value AS potvrzeni
FROM t_object a
INNER JOIN t_objectproperties r ON r.Object_ID = a.Object_ID AND r.Property = 'ai.risk.codes'
LEFT JOIN t_objectproperties m ON m.Object_ID = a.Object_ID AND m.Property = 'ai.risk.metrics'
LEFT JOIN t_objectproperties c ON c.Object_ID = a.Object_ID AND c.Property = 'ai.risk.confirm'
WHERE a.Package_ID IN (SELECT Package_ID FROM t_package WHERE ea_guid = '<GUID-AILOG>')
  AND a.Object_Type = 'Artifact'
  AND (r.Value = '<KOD>' OR r.Value LIKE '<KOD>;%' OR r.Value LIKE '%;<KOD>' OR r.Value LIKE '%;<KOD>;%')
ORDER BY a.CreatedDate DESC
```

Jen za určité období (po změně politiky) přidej do `WHERE` podmínku na `a.CreatedDate` — **ta jediná je dialektová**: SQLite `a.CreatedDate >= 'RRRR-MM-DD'` (text), MS SQL `a.CreatedDate >= 'RRRRMMDD'` (bez pomlček — jednoznačné při každém nastavení jazyka). Formát data v SQLite ověř prvním detailním dotazem (sloupec `kdy`).

**Postup:**

1. Pošli souhrnnou dávku (čtecí — okno neotevře, žádný zápis). `okno` = `potvrzeno` (Ano), `zamitnuto` (Ne), `vyprselo` (nikdo nerozhodl do 8 h), `bez okna` (LOW nebo BLOCKED — rozliší `uroven`).
2. Pro každý kód, který se v oknech objevuje (u kombinací rozpad detailním dotazem):
   - **vždy potvrzený** (jen `potvrzeno`, žádné `zamitnuto`) = **kandidát na zmírnění**;
   - **aspoň jednou zamítnutý** = zůstává;
   - `vyprselo` se nepočítá jako potvrzení; kód s méně než 5 okny za období nerozhoduj (doporučení — malý vzorek).
3. Kód → páka politiky (`src/AICodeBridge.FB_RiskPolicy.js`): `THRESHOLD_ELEVATED` → prahy `elevate` (který práh, řekne `metriky` v detailu); `CLASS_ELEVATED`, `CLASS_ELEVATED_FOREIGN` → mapa `classes`; `OWN_SESSION` → `ownSessionLow`; `MSG_REBUILD`, `OPS_PARAMS` a přepisy sad cizího prvku → fáze 2 `rebuildLowWithBaseline` (KONCEPCE pravidlo 9 — až po splnění jejích podmínek). Ostatní kódy (`CONFIG_TARGET`, `ROOT_PACKAGE`, `CASCADE`, `PREV_EXCEPTION`, `UNKNOWN_OP`, `POLICY_INVALID`, `BASELINE_*`, `HASH_MISSING`, `GATE_FAILED`, `RECLASS_*` …) jsou pojistky — kalibrací se nemění.
4. **Zápis změny politiky:** úprava položky repozitáře ve `FB_RiskPolicy.js` + komentář nad ní `// KALIBRACE RRRR-MM-DD <kdo>: <kód> potvrzen N/N oken za <období> -> <co se mění>`; doma `deploy_src` pumpou, v bance bootstrap + plný restart EA + kontrola parametrů (`NAVOD-NASAZENI-KLIKACI.md` 5.5, 5.7, 4a); řádek do changelogu KONCEPCE (`IT-ANALYSIS/KONCEPCE-potvrzovaci-okna-ea-file-bridge.md` kap. 8) s datem příští kalibrace (+4 týdny). ## 13. Vrátný — exit kódy a provoz (v0.9)

Exit kódy procesu vrátného (launcher/troubleshooting je rozliší):

| Kód | Význam |
|---|---|
| 0 | čisté ukončení (tlačítko **Ukoncit rezim** nebo zavření okna) — závěrečný souhrn do schránky + `session-log-*.md` |
| 2 | odmítnuto mutexem (druhá instance pro tentýž repozitář) — MessageBox, žádné okno, žádný dotyk `requests\`/schránky |
| 3 | reap (EA nedostupná déle než `reapTimeoutMin`) — session-log s důvodem REAP + seznamem nezpracovaných req; **schránka se při reapu nikdy nepřepisuje** |

**Mutex (W3):** `Local\EAFB_Gatekeeper_v1_<REPOKEY>` (REPOKEY = sanitizovaný `FB_RepoId`, delší než 32 znaků → 8 znaků MD5). Drží **proces vrátného, ne EA** — restart EA mutex nezruší, přeživší vrátný se re-attachne. Kill (Task Manager) → `AbandonedMutexException` → další launch mutex převezme (režim se nikdy trvale nezablokuje). Izolovaný test: `krok0\mutex-probe.ps1`.

**Reap + re-attach:** stavy `ATTACHED → REATTACHING → REAPING`, každý s vlastní reprezentací v okně. Identita repa po re-attachi se ověřuje **ping dávkou** (`FB_Process ping|<token>` → `gk-ping-*.json` s `repository`), porovnání **přesnou rovností** s `$RepoId` (ne podřetězcem — `<TEST-DB>` vs `<TEST-DB>_COPY`). Cizí/nenačtené repo → nepřisaje se, čítač timeoutu běží dál (W3 §3.3). Časy konfigurovatelné přes `gk-config.json` (default 10 min / 10 s / 15 s / 30 s).

**Provozní pravidlo:** v AI import režimu **jedna EA** (`GetActiveObject` neumí vybírat z ROT — H7). Vrátný spouštěný Z EA dědí elevaci EA (parita UAC — R2); nesoulad elevace → EA vypadá jako nedostupná (troubleshooting v návodu).
